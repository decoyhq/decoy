# Протокол воркера, версия 1

Здесь описано, какими сообщениями Decoy обменивается с воркером. Этот же протокол использует [TypeScript SDK](../transformer-sdk/index.mdx). По нему можно написать воркер на другом языке. Как подключить воркер к маршруту, описано в разделе [Настройка цепочки преобразований](../transformer-pipelines/index.md).

## Процесс

- Для каждой записи `transformers`, у которой `worker` задан списком аргументов, Decoy запускает один процесс в каталоге `decoy.yaml` и добавляет в его окружение `DECOY_TRANSFORMER=1`.
- `stdin` и `stdout` используются только для протокола. Любой посторонний вывод в `stdout` — ошибка протокола, после которой воркер завершится. Поэтому SDK направляет консольный вывод в `stderr`. В `stderr` допустим произвольный текст: Decoy выводит каждую строку как `[<key>: <name>@<version>] <line>` и сохраняет последние 20 строк для отчёта о завершении.
- Процесс живёт, пока работает Decoy. При остановке Decoy отправляет `shutdown` и принудительно завершает процесс, если он продолжает работать через 2 секунды. Если процесс завершился сам, Decoy сообщает код выхода и последние строки `stderr`, после чего завершается с ненулевым кодом. Decoy не перезапускает воркер даже при перечитывании конфигурации с `--watch`.

## Формат кадра

Первые 4 байта задают длину в порядке big-endian. За ними идёт один словарь MessagePack указанной длины. Лимит составляет 16 МиБ. Если воркер отправит более длинное сообщение, Decoy сочтёт это ошибкой протокола и завершит воркер. Если в лимит не укладывается `call`, Decoy не отправит его. Ошибка коснётся только этого кадра. В каждом словаре есть строковое поле `kind`.

## Значения

Значения кодируются в MessagePack. Сетевые байты — `bin`; всё остальное соответствует модели данных JSON (`nil`, `bool`, целые и дробные числа, `str`, массивы, словари со строковыми ключами). Транспорт определяет, как итоговое значение становится входом для Case или полезной нагрузкой в сетевом формате. См. руководства по [HTTP](../routes/index.md#http-body-pipelines), [gRPC](../grpc/index.md#pipelines) и [WebSocket](../websocket/index.md#websocket-pipelines).

## Сообщения

Decoy → воркер:

| `kind`       | Поля                                                                                  |
| ------------ | ------------------------------------------------------------------------------------- |
| `hello`      | `protocol: 1`, `decoy: "<version>"`                                                   |
| `call`       | `id`, `op` (`input`, `output`, `check`), `input`, `frame?`, `connection?`, `request?` |
| `hostResult` | `id` (из сообщения `host` воркера), `ok: true, value` или `ok: false, error`          |
| `close`      | `connection` (ID): удалить сохранённое состояние соединения                           |
| `shutdown`   | Без полей: завершить работу немедленно                                                |

Воркер → Decoy:

| `kind`   | Поля                                                                                  |
| -------- | ------------------------------------------------------------------------------------- |
| `ready`  | `protocol: 1`, `name`, `version`, `directions: [<input or output>]`                   |
| `result` | `id` (из `call`); `ok: true, value`, `ok: false, miss` или `ok: false, error, stack?` |
| `host`   | `id` (собственный счётчик воркера), `op`, `args: []`                                  |

## Установление связи

Decoy первым отправляет `hello`. Воркер отвечает `ready` со списком поддерживаемых направлений. Запуск прервётся, если воркер объявит другую версию протокола, завершится до готовности, не отправит корректное `ready` за 10 секунд или Pipeline использует необъявленное направление.

## Вызовы

- Decoy присваивает `call` идентификаторы, уникальные в пределах процесса воркера. Воркер может отвечать в любом порядке и выполнять вызовы параллельно. Следующий вызов для соединения Decoy отправляет только после ответа или истечения времени ожидания предыдущего. Поэтому шаг с состоянием для каждого соединения получает сообщения по порядку, если ожидание не истекло. После истечения времени ожидания запоздавший вызов может ещё выполняться даже после `close` для соединения.
- Вызовы WebSocket содержат `connection: { id, route, session }`. В HTTP, gRPC и проверках при запуске этого поля нет. Входной вызов WebSocket также содержит `frame` (`"text"` или `"binary"`).
- Вызовы `input` и `output` в HTTP передают `request: { method, path, headers }` вместе с полезной нагрузкой. `path` не включает строку запроса. `headers` — нормализованный словарь исходных заголовков: имена в нижнем регистре, значения — строки, в том числе `cookie` и `authorization`, если они есть. Воркерам не следует записывать эти значения в журнал. В вызовах не по HTTP и проверках запуска `request` отсутствует.
- `input` выполняется до проверки Cases. В WebSocket первый шаг получает полезную нагрузку фрейма как `bin`, а каждый следующий — результат предыдущего. Итог должен подходить для Message envelope этого транспорта.
- `output` выполняется над сформированной полезной нагрузкой Behavior, телом HTTP-ответа при Passthrough или сообщением от Control API. Каждый следующий шаг получает результат предыдущего. WebSocket отправляет итоговый `str` как текст, а `bin` — как двоичные данные.
- Если первым выходным шагом стоит воркер, при запуске он получает через `check` значение из конфигурации без преобразований и может его проверить. Воркер без обработчика `check` отвечает `ok: true`.
- Если входной шаг вернул `miss`, Decoy отмечает кадр как не подошедший под условие. На выходе `miss` означает ошибку преобразования.
- Задайте `timeout` в определении Transformer с суффиксом `ms` или `s`. По умолчанию — `5s`. При истечении времени Decoy сообщает об ошибке воркера и игнорирует запоздавший `result`.

## Вызовы хоста

Чтобы использовать загруженные Decoy данные, воркер отправляет `host`. Decoy отвечает `hostResult` с тем же `id`.

| `op`              | Аргументы       | Значение                                                            |
| ----------------- | --------------- | ------------------------------------------------------------------- |
| `protobuf.has`    | `[type]`        | `bool`: соответствует ли полное имя сообщению из proto-файлов Decoy |
| `protobuf.decode` | `[type, bin]`   | Сообщение в JSON, тот же словарь, который видят Case gRPC           |
| `protobuf.encode` | `[type, value]` | `bin`; для неизвестного поля возвращается ошибка с путём к полю     |

Во время проверок запуска (до начала обслуживания запросов; при перечитывании их нет) `protobuf.encode` только проверяет данные: строковые конечные значения с `${` пропускаются, имена полей и другие конечные значения по-прежнему проверяются, а результат — пустой `bin`.
