# Сессии и Control API

## Сессии {#sessions}

Заголовок `x-mock-session` указывает, к какой сессии (Session) относится запрос. Без него Decoy использует сессию по умолчанию. У каждой сессии свой **Selection**: активная коллекция и переопределения для отдельных маршрутов. Поэтому параллельные тесты могут менять ответы на одном сервере и не мешать друг другу.

Новая сессия начинает с коллекции по умолчанию. Decoy хранит до 10 000 сессий с заданным Selection. Если лимит превышен, Decoy завершает сессию, которую дольше всего не меняли, и выводит предупреждение. Это работает как `endSession`, но сессия по умолчанию под это правило не попадает.

## Control API {#control-api}

Отправляйте команды методом `POST` на зарезервированные пути `/__decoy__`. Укажите сессию в `x-mock-session`. Без этого заголовка команда действует в сессии по умолчанию. Передавайте `content-type: application/json` даже для `reset` и `endSession`. Другой тип даст `415`, поэтому страница с другого сайта не сможет переключить сценарий через форму или простой `fetch`.

| Команда         | Запрос                                  | Тело                                                                                              |
| --------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `useCollection` | `POST /__decoy__/control/useCollection` | `{"collection":"no-users"}`                                                                       |
| `useRoute`      | `POST /__decoy__/control/useRoute`      | `{"route":"users-by-id","case":"user-1","behavior":"grace"}`                                      |
| `reset`         | `POST /__decoy__/control/reset`         | Пустое или `{}`: удаляет переопределения Routes Session.                                          |
| `endSession`    | `POST /__decoy__/control/endSession`    | Пустое или `{}`: завершает Session; при следующем обращении она начнётся с настроек по умолчанию. |

`useRoute` меняет правило Behavior для пары `route:case`, не меняя её места в активной коллекции. У записей ниже по списку по-прежнему выше приоритет. Если такой пары в коллекции нет, Decoy добавляет её в конец. У записей, добавленных таким способом, приоритет выше у той, что добавили последней.

При успехе Decoy возвращает `200` с Selection для текущей Session. Неизвестные Collections или Behavior addresses, некорректный JSON и неизвестные поля тела дают `400 {"error":"..."}`. Если не указан тип содержимого JSON, возвращается `415`, а для неизвестных путей `/__decoy__` — `404`.

```sh title="Override a Behavior in test-42"
curl -X POST localhost:8080/__decoy__/control/useRoute \
  -H 'x-mock-session: test-42' \
  -H 'content-type: application/json' \
  -d '{"route":"users-by-id","case":"user-1","behavior":"grace"}'
```

## send

`POST /__decoy__/control/send` отправляет сообщение в активные соединения Route: открытые [вызовы gRPC с серверной потоковой передачей](../grpc/index.md#server-streaming) и сокеты [WebSocket](../websocket/index.md).

```sh title="Push a gRPC message in test-42"
curl -X POST localhost:8080/__decoy__/control/send \
  -H 'x-mock-session: test-42' \
  -H 'content-type: application/json' \
  -d '{"route":"approvals-watch","message":{"id":"a-1","state":"APPROVED"},"timeout":2000}'
```

- gRPC: Decoy кодирует `message` перед постановкой в очередь. Для стандартного кодека используйте protobuf JSON; для своего выходного Pipeline — значение, которое ожидает его первый шаг. При ошибке кодирования Decoy возвращает `400` с причиной и ничего не ставит в очередь.
- WebSocket: Decoy ставит `message` в очередь до запуска выходного Pipeline на каждом соединении-получателе. При ошибке преобразования Decoy записывает её и пропускает фрейм; API всё равно учитывает поставленное в очередь сообщение. Без выходных шагов строки отправляются как есть, остальные значения — как текст JSON.
- Сообщение получают только соединения той же Session (`x-mock-session`).
- Если открытых соединений пока нет, `send` ждёт до `timeout` миллисекунд (по умолчанию `5000`, не более 5 минут: более длинное значение урезается).
- В каждом соединении может быть до 64 непрочитанных сообщений в очереди. Соединение с полной очередью пропускает сообщение и не входит в `delivered`. Если все очереди полны, `send` ждёт, как описано выше.
- После [перечитывания конфигурации](../config/index.md#reloading) `message` кодируется текущим выходным типом, в том числе для потоков, открытых до этого. Старый клиент пропускает незнакомые поля. Поток, чей Route теперь отвечает сообщением другого типа, не получит его.

| Статус | Когда возвращается                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `200`  | `{"delivered":<n>}`: сколько соединений приняли сообщение в очередь.                                                                  |
| `400`  | Некорректное тело запроса или `message` не кодируется для Route gRPC.                                                                 |
| `404`  | Неизвестный Route.                                                                                                                    |
| `409`  | У Route нет долгоживущих соединений (HTTP, унарный gRPC).                                                                             |
| `408`  | За время ожидания его не приняло ни одно активное соединение Route в этой Session: их нет, очереди полны или используется старый тип. |
| `503`  | Decoy завершает работу.                                                                                                               |

Как и у других команд, некорректный JSON или неизвестное поле тела дают `400`, а отсутствие типа содержимого JSON — `415`.

## wait

`POST /__decoy__/control/wait` с `connected: true` завершается, когда в Session вызывающей стороны появляется активное соединение Route. Тогда тест может вызвать `send`, зная, что сокет или поток страницы открыт.

```sh title="Wait for a connection in test-42"
curl -X POST localhost:8080/__decoy__/control/wait \
  -H 'x-mock-session: test-42' \
  -H 'content-type: application/json' \
  -d '{"route":"friend-socket","connected":true,"timeout":2000}'
```

- Учитываются только соединения той же Session (`x-mock-session`), до которых дойдёт `send`: сокет WebSocket подходит всегда; поток gRPC — только пока открыт для `send` (у его Case нет `status`) и если он был открыт с текущим выходным типом Route. Конечный поток по Scenario (его Case завершается статусом `status`) не регистрируется, поэтому `wait` отвечает `408`.
- Время ожидания — до `timeout` миллисекунд (по умолчанию `5000`, не более 5 минут).
- Пока `wait` умеет ждать только открытия соединения (`connected: true`).

| Статус | Когда возвращается                                                           |
| ------ | ---------------------------------------------------------------------------- |
| `200`  | `{"connections":<n>}`: сколько таких соединений открыто в этой Session.      |
| `400`  | `connected` отсутствует, не равен `true` или задано другое Case (`message`). |
| `404`  | Неизвестный Route.                                                           |
| `409`  | У Route нет долгоживущих соединений (HTTP, унарный gRPC).                    |
| `408`  | За время ожидания в этой Session не открылось активное соединение Route.     |
| `503`  | Decoy завершает работу.                                                      |

Как и у других команд, некорректный JSON или неизвестное поле тела дают `400`, а отсутствие типа содержимого JSON — `415`.

## Проверка работоспособности

Пока сервер принимает запросы, `GET /__decoy__/health` возвращает `200 {"status":"ok"}`. Запрос не проверяет маршруты и не меняет сессии.
